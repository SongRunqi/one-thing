# 句柄编解码闭合 —— 识别与授权分家

> 状态：设计，未实施
> 日期：2026-08-01
> 相关：`collab-agent-handle.md`（句柄机制本体）、`agent-dm-user.md` §2.3（用户句柄）、`multi-agent-collab-im.md` §4.5（W14a 身份 id 化）

## 1. 问题：这是一个编解码器，而它不是全函数

句柄机制本质是一对编解码：

- **编码（出站）**：把身份写进送给模型的文本 —— `名字#句柄`；
- **解码（入站）**：落库前从正文里认出来、搬进 `mentions[]`、把 `#句柄` 删掉。

它成立的唯一条件是 **`解码(编码(x)) = 干净文本`，对身份域里的每一个 x 都成立**。现在不成立，而且缺口是结构性的——两个轴各自都漏：

**轴一·身份域。** 编码会给谁发句柄：

| 身份 | 编码发不发 | 解码认不认 |
| --- | --- | --- |
| 在职房间成员 | 发（花名册、信封、@重绘） | ✅ 认 |
| 用户本人 | 发（`songyitian#666666(用户)`） | ❌ 不认 |
| 退休 / 离群成员 | 发（`resolveCollabSpeakerLabel` 明确规定「照样给句柄」） | ❌ 不认 |
| 非本房 agent | 发（看板摘要里的指派人） | ❌ 不认 |

根因一句话：解码用的名单是 `roomMembers()`，它同时承担了两个互不相干的职责——**「谁能被识别」**和**「谁能被激活」**。后者理应严格（在职、在本房），于是前者被一起收窄了。**识别面被授权面绑架**，这是整个 bug 的来源。

**轴二·形态域。** 编码会写出的形状：

| 形状 | 谁在发 | 解码认不认 |
| --- | --- | --- |
| `@名字#句柄` | 正文 @ 重绘（`renderCollabModelMention`） | ✅ 认 |
| `名字#句柄`（裸的） | 花名册行、信封 `from`、意愿窗口、看板摘要 | ❌ 不认 |
| `#句柄`（独立成词） | dm 工具描述教的写法 | ❌ 不认 |

解码器 `scanCollabHandleMentions` 只扫紧跟 `@` 的那一种。而花名册教的恰恰是**裸形态**。

**实测数据**（当前 store，19 个 room 会话的正文）：

```
@名字#句柄   6 处   全部是用户的
名字#句柄   29 处   用户 13 + agent 16（Bram/Nova/Atlas/Iris 都有）
```

裸形态是带 @ 的 5 倍。**这不是「用户漏了」，是编解码器在两个轴上都不是全函数。**

### 1.1 它会自我放大

模型在转录里看见句柄 → 认为句柄是可以在对话里讨论、试验的东西 → 写更多句柄 → 下一轮看见更多。现场证据是 agent 私聊用户失败后在群里公开试格式：

> 「之前 Iris 用 `用户` 去调 dm，可能得用 `#666666` 或者 `用户#666666` 才认。我试试看」

`用户#666666` 这种写法代码从没发过——是模型把花名册给的句柄和工具描述给的常量词 `用户` 拼出来的。**泄漏一旦发生，模型会衍生出代码从未产生过的新变体**，所以"逐个变体去补"这条路走不通。

## 2. 方案：一份身份目录，两处共用

### 2.1 核心：把识别面从授权面里拆出来

新增**身份目录**，作为编解码双方的唯一真源。

```ts
// packages/onething-runtime/src/collab/identity.ts（纯逻辑）
export interface CollabIdentity {
  kind: 'agent' | 'user'
  /** agent 才有。用户没有 agent id —— 这里就是缺席,不造假 id。 */
  agentId?: string
  handle: string
  /** 主名(显示用)。 */
  label: string
  /** 还能用什么写法指认 TA:用户是 ['用户','user'],agent 只有本名。 */
  aliases: readonly string[]
}
```

```ts
// packages/onething-runtime/src/app/collab/identity-directory.ts（接线）
export function buildCollabIdentityDirectory(): CollabIdentity[]
```

内容：**全体 agent（含退休）+ 用户**。

为什么是全体而不是房内成员——这正是修复的要点：

- **识别面要尽可能全**。解码的判据是「这串字符是不是一个真身份」，识别得越全，清理得越干净。模型完全可能在 A 房里提到 B 房的同事（看板指派人就是现成的例子），那个句柄同样该被剥掉。
- **授权面照旧严格**。放宽识别**不会**让任何人被误唤醒：`activation.ts` 的两条路径本来就各自 `.filter(agentId => memberIds.has(agentId))`，非成员进不了激活队列。

一句话：**识别归目录，授权归成员名单，两者不再共用一个数组。**

### 2.2 形态：裸句柄按「名实相符」剥

解码器扩到裸形态，但判据分级——这是为了不与看板短卡号 `#a1b2c3d4` 撞车（两者都是 `#` + 8 位，`collab-agent-handle.md` §3 专门警告过）：

| 形状 | 判据 | 理由 |
| --- | --- | --- |
| `@名字#句柄` | **句柄说了算**，名字对不上也剥 | 这是一次点名行为，与既有 agent 口径一致（模型可能拿旧名字配新句柄） |
| `名字#句柄`（裸） | **名实必须相符**：`#` 前的词必须是该句柄所属身份的 `label` 或 `aliases` 之一 | 这是叙述，保守。卡号引用永远不会把指派人的名字粘在 `#` 前面，所以结构上撞不了车 |
| `#句柄`（独立成词） | **不剥** | 这一格是卡号的地盘，无法在不引入看板耦合的前提下区分。已知残留，见 §4 |

`用户#666666` 会被这条规则吃掉，因为 `用户` 在用户身份的 `aliases` 里——常量词表与 `dm-target.ts` 的 `USER_CONSTANT_WORDS` 共用一份，不另抄。

### 2.3 `mentions[]` 携带用户身份

现状是名字匹配：渲染层认「@我」只认两个常量 `['用户','我']`，而你的显示名是 `songyitian` —— 就算把 id 剥干净成 `@songyitian`，它仍然渲染成普通文字，不是 pill。而名字匹配正是 W14a 当初为 agent 废弃掉的东西（改名即失效、重名不可分辨）。用户不该退回那条老路。

```ts
// packages/shared/ipc/chat.ts
export interface ChatMessageMention {
  agentId: string
  label: string
  /** 缺省 'agent'（老转录即此）。'user' = 这一处点的是用户本人。 */
  kind?: 'agent' | 'user'
}
```

用户那一条的 `agentId` 留**空字符串**。这是刻意的：

- **它是诚实的**——用户确实没有 agent id，编一个合成 id 才是撒谎，而合成 id 会在某天被人当真去 `findAgent`；
- **它是安全的**——所有消费方本来就有空值门。`unionTurnMentions` 是 `if (!mention?.agentId) continue`，`normalizeCollabMentions` 是 `if (!agentId) continue`。用户条目天然不进激活、不进成员校验，**零改动即安全**。

（考虑过判别联合 `{kind:'user'; label}`，放弃：为三处读取方改全仓的类型收窄，收益不抵成本。）

### 2.4 渲染层按 kind 认人

`@我` pill 的判定改为**两级**：

1. `mentions[]` 里有 `kind:'user'` 的条目 → 按 id 级的确定性认（新消息走这条，改名不失效）；
2. 没有（老转录）→ 退回既有 `userLabels` 名字匹配，且把 `resolveUserIdentity().label` 喂进去，不再只有两个常量。

第 2 条的管子**已经存在**——`renderCollabMentionMarkup` 和 `renderCollabMentionText` 都已经有 `userLabels` 参数，只是从没被喂过真实档案名。

### 2.5 不变式测试（本方案真正的交付物）

前面四节都是修，这一节是**防复发**。一条属性测试，遍历身份域 × 形态域的全乘积：

```
for 身份 in [在职 agent, 退休 agent, 非本房 agent, 用户]
  for 形态 in [@名字#句柄, 名字#句柄, @#句柄]
    assert strip(编码(身份, 形态), 目录) 不含该身份的句柄
assert strip('完成 #463fc4ca 了', 目录) === '完成 #463fc4ca 了'   // 卡号不许被吃
```

12 + 1 条。它的价值不在这 13 条本身，而在于：**新增一种身份、或新增一个出站点却忘了解码路径，这条测试会红。** 这次的 bug 之所以能活下来，正是因为没有任何一条测试同时看着编码和解码两侧。

## 3. 实施顺序

| 期 | 内容 | 风险 |
| --- | --- | --- |
| **F1** | `collab/identity.ts` 目录类型与匹配规则 + `handles.ts` 解码改造（作用域 + 裸形态）+ §2.5 不变式测试 | 低（纯逻辑，测试先行） |
| **F2** | `app/collab/identity-directory.ts` 接线；`say-tool` 剥离改用目录；`dm-target` 的用户匹配并入目录（消掉那份重复的常量词表） | 低 |
| **F3** | `ChatMessageMention.kind` + say 解码产出用户条目 + 渲染层两级判定 | 中（碰 shared 类型，需过一遍消费方） |
| **F4** | 历史清理脚本（见 §4） | 中（改用户数据，必须 dry-run 先行） |

F1+F2 就能止住新增泄漏；F3 是把「@我」从名字匹配升级成身份匹配；F4 是打扫。

## 4. 边界、取舍与已知残留

**独立成词的 `#句柄` 不剥。** 与看板短卡号形状完全相同且无上下文可依。要根治只有两条路：给两者不同的形状（破坏既有转录），或让解码器去查看板（引入跨域耦合）。两条都不值当。残留量：当前 store 里 0 处。

**工具结果与工作会话不剥，按设计。** 看板摘要 `@Atlas#7185be2b`（工具返回）和 agent 原始输出（`agent-exec` 会话正文）都是模型面文本，剥了反而破坏模型视野。但**用户能看见它们**——前者在工具卡、后者在「展开执行」右栏。可选加一层**显示层剥离**（只在渲染时过一遍，不改存储）；建议等 F1–F4 落地后再看是否还刺眼，不要一次改太多。

**历史 35 处不会自愈。** 落库即定型。脚本口径：只处理 room 会话、只改 `content`、只剥能在目录里解析出身份的句柄、默认 dry-run 打印将改动的行数与样本、`--apply` 才写、写前按既有 `sessions/legacy-backup/` 惯例留原件。

**考虑过、放弃的替代方案：不给用户发句柄。** 这能一举消掉泄漏量最大的那一个 token（17/35），而且能力上不亏——`dm-target.ts` 的常量词 `用户`/`user` 本来就永远可达，重名冲突也已有拒绝逻辑。放弃的理由：它只治用户这一例，退休成员、非本房成员两类照旧漏；而只要按 §2.1 把编解码域闭合，用户这一例是**顺带修好的**。**修编解码器，不修实例。**

**性能。** 目录每次 `say` 构建一次，规模是 agent 总数（几十），且只做字符串切片与 Map 装填。相对于一次工具调用可忽略，不做缓存——缓存意味着要有人负责在改名/注销后让它失效，而那个"有人"正是这类 bug 的出处（`user-identity.ts` 的注释已经把这条纪律写过一遍）。

## 5. 验收

1. agent 在群里写 `@小李#3f9c1e2a`、`小李#3f9c1e2a`、`@#3f9c1e2a` 三种写法，房间转录里全部是干净的 `@小李`；
2. agent 提到用户（`@songyitian#666666` / `` `用户#666666` ``），转录里是 `@songyitian`，且中栏渲染成「@我」pill；
3. 提到退休成员、非本房成员，句柄同样被剥；
4. 正文里的 `#463fc4ca`（卡号）原样保留；
5. 用户改名后，旧消息里的「@我」pill 仍然认得出（走 `kind:'user'`，不依赖名字）；
6. 非本房成员被提及**不会**被激活（授权面未被放宽）；
7. §2.5 不变式测试全绿。
