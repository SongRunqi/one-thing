## 一、这份文档讲什么

最近给「思考模式」做全 provider 支持时，暴露出一类结构性问题：**同一件事实，代码里记了很多本账，各本账各自演化，答案开始不一样。**

排查后确认：这不只是「模型能力」一处的问题，设置系统里同一类问题有三种表现。本文档把两条治理线整合成一个路线图：

- **A 线（模型能力线）**：「模型 X 能不能思考/看图/调工具、思考有哪些档位」——这件事目前有六本账。
- **S 线（设置读写线）**：「某个开关没设置时算开还是关」「数字默认值是多少」「设置怎么保存」——这三件事各处自己约定。

---

## 二、问题的本质：一件事，多本账

### 案例 1：「这个模型支不支持思考」——六本账（A 线核心问题）

程序里有六个地方各自回答这个问题，判断依据互不相同：

| 账本 | 在哪用 | 现状 |
|---|---|---|
| 账本 1 | 后台模型注册表（异步版判断函数） | **已确认没有任何地方在调用它**——是一本没人看却还在维护的死账 |
| 账本 2 | 同一个注册表的同步版判断函数 | 同样没人调用，而且**判断规则和账本 1 已经不一样了**（一个排除某些 GPT 型号，一个不排除） |
| 账本 3 | GitHub Copilot 的模型列表构建 | 用一份自己的型号名单猜测能力，还顺带硬编码了各模型的上下文长度 |
| 账本 4 | 设置页的能力图标（"这个模型会思考"的小标) | 又一份不同的型号名单 |
| 账本 5 | 输入框的思考开关（ThinkToggle） | 2026-07-18 实现思考功能时新加的第五份名单（当时为了不动进程间通信走的捷径） |
| 账本 6 | 各 provider 的请求代码 | 「Claude 哪一代用哪种参数」「Gemini 2.5 和 3 参数不同」这类代际知识，散在五六个文件里 |

**后果**：界面上显示「这个模型会思考」和引擎实际发不发思考参数，走的是两条不同的判断链。这与之前「选 deepseek 却走了 codex」的事故是同一个病：UI 一套解析、引擎一套解析，总有一天答案不同。那次事故的解法（统一为单一规则 + 镜像测试）应该在这里重演。

### 案例 2：「开关没设置时算开还是关」——各处自己约定（S 线问题一）

设置文件里大量开关允许「没设置」状态。没设置算什么，全靠每个读取处自己写判断：

- 「不等于关就算开」（默认开）这种写法，界面代码里有 18+ 处、引擎代码里有 10+ 处，**各自手写**。
- 「provider 是否启用」这一个判断，在 6 个不同的界面文件里各写了一遍。
- **已发生的实锤**：思考开关旧代码里，界面按「默认开」显示，引擎按「明确设了才发」执行——DeepSeek V4 界面显示思考已开启，引擎实际什么参数都没发。显示和行为不一致，用户无从察觉。

目前大部分地方的约定恰好一致，所以没出更多事故——但没有任何护栏阻止下一个人写出不一致的判断。

### 案例 3：数字默认值三层散落（S 线问题二）

- 共享默认值文件里定义了「默认温度 0.7、默认最大输出 4096」等；
- 但引擎里另有本地常量（如「最大轮数默认 100」定义在引擎文件里，不在默认值文件里）；
- 还有直接写死在调用点的（Claude 请求代码里自己写了个 4096）。

另一类更隐蔽：**取值范围没有按 provider 区分**。温度设置界面允许 0～2，但 Anthropic 只接受 0～1、最新几代模型设了温度直接报错——现在是引擎悄悄丢弃这个参数保平安，界面完全不知道，滑块照样可以拖。这和「模型能力」是同一个病：参数的合法范围本身就是一种「模型能力」，但没有事实源。

### 案例 4：保存方式不统一（S 线问题三）

绝大多数设置更新走「只改这一个字段」的专用通道；但思考开关（沿用旧模式）是**把整个设置对象读出来、改一处、整体写回**。如果此时其他地方也在改设置，后写的会覆盖先写的。目前只此一处，但它是并发覆盖事故的火种（会话索引文件已经出过同类竞态，后来加了锁）。

### 为什么会变成这样

不是谁写错了——每次加新功能时，就近记一笔账最快：加个开关就地写个「不等于关就算开」，加个模型就地写份型号名单。单看每一笔都合理，积累起来就是六本账。治理的目标不是追责，是**把「就近记账」的路堵掉，让唯一账本成为最省事的选择**。

## 三、目标：一件事，一本账

三条原则，之后所有实施都对照它们验收：

1. **唯一事实源**：每个问题（某模型有什么能力、某开关默认状态、某数字默认值）在代码里只有一处定义。其他所有地方——界面、引擎、设置页——都问它，不许自己另记。
2. **界面与引擎同源**：界面上显示的状态和引擎实际的行为，必须出自同一个判断函数，而不是「两套代码遵循同一份口头约定」。
3. **镜像测试护栏**：用自动化测试固化「界面答案 = 引擎答案」，任何人改了一侧、另一侧没跟上，测试立刻红。这是 provider 解析统一那次验证过的有效手段。

### A 线的核心设计（白话）

建一个**「模型能力台账」模块**：输入 provider 和模型名，输出这个模型的全部能力答案——能不能思考、看图、调工具，思考能不能关、默认开不开、有哪些档位、参数在线上怎么表达。判断顺序全局统一：**用户手动覆盖 > provider 直接下发的元数据 > 联网拉取的模型注册表 > 内置规则表 > 默认值**，并且每个答案都标注「是从哪一级得出的」（方便排查）。

六本账的处理：两本死账直接销毁；三份型号名单合并进台账的内置规则表；各 provider 的代际知识（档位表、参数预算数值）也收进台账，provider 请求代码和界面档位选单都从台账取数——现在这两处是平行维护的两份手抄，改一处忘一处。

Codex 已经示范了正确模式（模型元数据驱动界面选项），方案就是把这个模式推广到所有 provider。

### S 线的核心设计（白话）

1. **设置读取器**：每个设置项配一个唯一的读取函数，「没设置算什么」的语义写在函数里，界面和引擎都只许通过它读。散落的 28+ 处手写判断逐步收编。
2. **默认值归一**：所有数字默认值收进共享默认值文件，引擎本地常量和调用点写死的数字全部改为引用；参数取值范围（如温度上限）并入 A 线的能力台账，按 provider 给答案，界面滑块据此调整范围。
3. **写入统一**：废除「整对象读改写」，思考开关改走分字段更新通道，与其他设置一致。

## 四、路线图

两条线交织排期，每期独立完成、独立验收、独立提交。总量约 5～6.5 天。

| 期 | 线 | 内容一句话 | 量 | 依赖 |
|---|---|---|---|---|
| **第 0 期** | A | 勘察：界面能不能直接调用台账模块（涉及架构边界规则），拍板取数通道 | 0.5 天 | 无 |
| **第 1 期** | A | 建模型能力台账 + 内置规则表；销毁两本死账、收编三份名单；上镜像测试 | 1.5–2 天 | 第 0 期 |
| **第 2 期** | S | 设置读取器：思考相关的读取先收编（顺路修 DeepSeek 显示与行为不一致），再收编 provider 启用等高频判断 | 1 天 | 第 1 期（思考语义已定） |
| **第 3 期** | A | 档位与参数预算全部由台账驱动：界面选单、provider 参数映射从同一张表取数；输入框思考开关里的分 provider 逻辑坍缩 | 1 天 | 第 1 期 |
| **第 4 期** | A | 能力查询按「当前模型」实时回答（现在是 provider 创建时定死一份，会话中途换模型不会更新）；顺带解决模型列表刷新后能力过期的问题 | 0.5 天 | 第 1 期 |
| **第 5 期** | S | 数字默认值归一到共享默认值文件；温度等取值范围并入台账按 provider 区分；思考开关改分字段保存 | 0.5–1 天 | 第 1、2 期 |
| **第 6 期** | A | 清理：静态模型表、Copilot 硬编码上下文表收编台账；旧的双层包装文件缩为转发（配合 src 目录薄化的大方向）；删除其余确认无人调用的死代码 | 0.5–1 天，可延后 | 前五期 |

### 各期验收标准（白话）

- **第 0 期**：给出一句话结论——界面直接调台账函数，还是通过现有的模型列表通道捎带台账结果。前者保证最强（字面上同一个函数），需要过架构边界测试并同步两份构建配置（历史上漏同步过，只有完整构建能暴露）。
- **第 1 期**：全库搜索不到六本账中任何一本的残留；镜像测试覆盖每个 provider 的代表模型；对现有行为的任何有意变更（比如死账里那条「排除某 GPT 型号」的规则要不要保留）逐条写进测试注释。现有界面行为不变（用固化快照对比）。
- **第 2 期**：DeepSeek V4 的显示与行为一致；「provider 是否启用」判断在界面代码里只剩一处定义。
- **第 3 期**：输入框思考开关组件里不再有任何按 provider 名分支的档位常量；改一个档位数值只需改台账一处。
- **第 4 期**：新增测试证明——同一个 provider 下两个能力不同的模型（比如 Copilot 下的有图模型和无图模型）能得到不同的能力答案。
- **第 5 期**：全库搜索不到调用点写死的默认数字；温度滑块在选中 Anthropic 新模型时消失或禁用（而不是设了被悄悄丢弃）。
- **第 6 期**：旧包装文件只剩转发；死代码清零。

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| 统一后行为和现网六本账的答案不一致，用户感知变化 | 先用测试快照固化现状，再统一；有意变更逐条标注，不搞静默改判 |
| 界面调台账模块违反架构边界 | 第 0 期先勘察；不行就走模型列表通道捎带，界面零本地判断 |
| 两份构建配置漏同步（历史踩过） | 第 0 期清单项；以完整构建通过为准，不以启动成功为准 |
| 设置文件格式变化引发迁移 | **不会发生**：所有台账内容都是推导出来的，不落盘，设置文件一个字段都不加 |
| 与在途未提交工作（练习系统、设置页改版等）冲突 | 每期独立提交；不触碰在途改动的文件；设置页改版若先落地，第 2 期顺延适配 |
| 主进程与包目录存在镜像测试双份 | 迁移时两侧同步改（本次思考功能已踩过一次，有先例可循） |

## 六、实施前需拍板的三件事

1. **第 0 期通道选择**：界面直接调用台账（最强保证）vs 走模型列表捎带（最保守）。倾向前者。
2. **provider 参数风格标识**是否在第 3 期就改由台账推导（现在是创建 provider 时手工指定的字符串，语义与台账重复）。建议改。
3. **第 6 期是否本轮做**：它与 src 目录薄化方向重叠，建议单独排期，避免重复劳动。
