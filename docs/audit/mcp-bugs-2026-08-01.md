## P0-1 · web 端 MCP 工具对模型完全不可用（双管理器分裂，且静默）

**严重度**：高 · 功能整体失效 · 无任何报错

**根因**：服务端存在**两个互不相干的 MCP 管理器**。

- `/api/mcp/*` 走 `apps/server/src/runtime.ts:7699` 的 `getOwnerMCPManager()` —— 一个 **per-owner 的 `HeadlessMCPManager`**。
- 而引擎执行工具走 `packages/onething-runtime/src/app/mcp/bridge.ts:24` 的 `coreMCPBridgeRuntime`，
  它硬绑在 **app 层单例 `MCPManager`** 上（`app/engine/stream/tool-execution.ts:69`、`stream-processor.ts:69` 均从这里取）。
- `apps/server/src/runtime.ts:1198` 的 `createOnethingBackend({...})` **没有传 `mcpAcp`**
  （只有 `toolRegistry` / `sessionSkills` / `sender`），
  而 `backend.ts:187` 的 `MCPManager.initialize()` + `registerMCPTools()` 只在 `options.mcpAcp` 为真时执行。

对照：桌面端在 `apps/electron/src/app/main-process.ts:217` 单独调 `initializeMCP()`；
CLI daemon 在 `app/headless/backend.ts:96` 传了 `mcpAcp: true`。**只有 apps/server 两条路都没走。**

**表现**：web 端加一个 MCP server → UI 显示"已连接"、工具列表也拉得到 →
但单例 `MCPManager.getAllTools()` 永远是 `[]` →
`getMCPRouterToolDefinition()`（`core/mcp/bridge-runtime.ts:76`）返回 `null` →
**`mcp_search` 根本不进模型的工具列表**。用户看不到任何错误。

**复现**：起 `bun run server:start`，浏览器进设置页加一个 stdio/SSE server，等状态变绿，
然后在对话里让模型用该 server 的工具 —— 模型会说没有这个工具。

**修复方向**：二选一，但必须选一个真源。
- (a) `createRealServerBackend` 传 `mcpAcp: true`，并让 `/api/mcp/*` 复用同一个单例（推荐，与 session 仓储"双仓储根除"同一道理）；
- (b) 若坚持 per-owner 隔离，则引擎侧的 bridge 必须可注入 manager，不能硬绑单例。

> 这条是 07-26 架构审查里"server 平行应用层"那笔债在 MCP 上的具体兑现。

## P0-2 · 关掉再打开 / 修好配置后不会重连

**严重度**：高 · 高频用户路径

**根因**：`updateMCPClientConfigWithAdapters`（`core/mcp/client-state.ts:386`）用
`wasConnected = state.status === 'connected'` 决定要不要重连（`:408`）。
而 `HeadlessMCPManager.updateSettings`（`core/mcp/manager.ts:92-104`）对**已存在的 client** 一律走 `client.updateConfig(config)`。

`disconnectServer` 只断开、**不从 `clients` map 移除**（`manager.ts:124`），于是：

| 场景 | 结果 |
| --- | --- |
| 从未启用过的 server 打开 | ✅ 正常（`clients.get()` 为空 → 走 `connectServer`） |
| 启用→连上→关掉→**再打开** | ❌ client 存在且 disconnected → `wasConnected=false` → **只改配置不连接** |
| 启动时连接失败（status=`error`）→ 用户改命令想修好 | ❌ 同上 → **不会重试**，必须手动点"连接" |

第二种是最疼的：用户把 `command` 打错了，改对之后保存，界面依然红着。

**触发路径**：`MCPServerItem.vue:51` toggle → `useMCPServers.ts:53 toggleServerEnabled`
→ `mcpUpdateServer` → `updateOnethingMCPServer` → `manager.updateSettings`。

**修复方向**：判定条件从 `wasConnected` 改成 `wasConnected || (config.enabled && 旧配置未启用/连接失败)`；
更干净的做法是让 `updateConfig` 的语义变成"向目标状态收敛"——目标由 `config.enabled` 决定，而非由当前状态决定。

## P1-1 · MCP 工具返回的图片被 JSON 序列化成文本灌进上下文

**严重度**：高（保真 + 上下文炸裂双重）

**根因**：模型调 MCP 工具的**唯一路径**是 router。`executeMCPBridgeTool`（`core/mcp/router.ts:558`）在拿到结果后无条件做：

```ts
const text = mcpContentToString(result.content)
return { success: true, content: [{ type: 'text', text }], isError: result.isError }
```

而 `mcpContentToString`（`router.ts:207`）对非 text 项是 `JSON.stringify(item)`。
image 项形如 `{ type:'image', data:'<整段 base64>', mimeType }` → **整段 base64 被塞进一个 text 字符串**。

**影响**：playwright / chrome-devtools / 任何返回截图的 MCP server，
既拿不到真正的图片（模型看不到图），又把几百 KB base64 当文本计费进上下文。
这正是 [上下文膨胀那次修复](../design/) 里已经打过的同一类洞，只是 MCP 这条路没覆盖到。

**修复方向**：router 的 `call` 分支不要把 content 压扁 —— 原样透传 `result.content`，
只对需要给模型看的摘要做 text 化。

## P1-2 · 只要填了任意一个 env 变量，主进程整个环境（含各家 API key）就泄漏给 MCP 子进程

**严重度**：高（安全）· 且行为不一致

**根因**：`mergeMCPEnvironment`（`core/mcp/client-state.ts:249`）：

```ts
if (!customEnv) return undefined
return { ...filterStringEnvironment(baseEnv), ...customEnv }   // baseEnv = process.env
```

- 不填 env → 传 `undefined` → SDK 用 `getDefaultEnvironment()` 的**安全白名单**
  （实测 `node_modules/@modelcontextprotocol/sdk/dist/esm/client/stdio.js:8`：非 Windows 只有 `HOME/LOGNAME/PATH/SHELL/TERM/USER`）。
- 填了**任意一个** env → 我们把 **`process.env` 全量**合并后传下去，
  SDK 再叠一层默认值（`stdio.js:67`）。

于是"给某个 MCP server 加一个 `GITHUB_TOKEN`"这个动作，会顺带把主进程里
所有 provider 的 API key、OAuth token、`ONETHING_*` 配置全部交给这个第三方子进程。
用户完全不会预期这一点，UI 上也没有任何提示。

**修复方向**：不要合并 `process.env`。只传 `customEnv`（SDK 自己会补安全白名单）；
若确实需要继承某些变量，做成显式的"继承变量白名单"设置项。

## P1-3 · 模型把 arguments 传成 JSON 字符串时，工具以空参数静默执行

**严重度**：中高 · 静默错误

**根因**：`resolveMCPRouterAction`（`core/mcp/router.ts:529`）`args: objectArgument(args.arguments)`，
而 `objectArgument`（`:472`）只认真正的 object，**字符串一律返回 `{}`**：

```ts
return value && typeof value === 'object' && !Array.isArray(value) ? value as JsonObject : {}
```

模型（尤其经 openai-compatible 通道）把嵌套参数二次编码成 JSON 字符串是常见行为。
一旦发生，MCP 工具会**带着空参数被真的执行**，然后返回一个语义上莫名其妙的结果，
既不报错也不提示 —— 排查成本极高。

而 zod 校验这条防线是**死的**（见 P2-2），所以没有任何兜底。

**修复方向**：`objectArgument` 对字符串先试 `JSON.parse`；解析失败则返回明确错误，不要静默降级成 `{}`。

## P1-4 · 工具调用超时后串行锁提前释放，同一 server 会出现并发请求

**严重度**：中

**根因**：`CoreMCPClientRuntime.callTool`（`core/mcp/client-runtime.ts:122`）用 `toolCallQueue` 串行化，
注释明确写着"stdio 传输 / 有状态 server 不耐受交错请求"。
但超时是 `withMCPTimeout` 的 `Promise.race`（`client-state.ts:567`）——
**超时只让我们这边的 promise 落地，底层 `client.callTool` 仍在飞**。
队列因此提前放行下一个调用，于是同一个 stdio server 上出现两个 in-flight 请求，恰好破坏了这段代码想保证的不变量。

叠加现状 R4（超时不发 `notifications/cancelled`），服务端那次调用会一直跑到底。

**修复方向**：超时时向服务端发取消，并等取消确认（或至少等底层 promise settle）后再释放队列。

## P2-1 · 连接失败被吞，UI 报"成功"

**严重度**：中

`HeadlessMCPManager.connectServer`（`core/mcp/manager.ts:120`）`catch` 后只 `console.error`。
上层 `connectOnethingMCPServer`（`runtime/src/mcp/server-orchestration.ts`）
`await manager.connectServer(config)` 之后无条件 `return { success: true, ... }`。

于是点"连接"永远返回成功；用户只能靠随后刷新出来的 `status: 'error'` 才发现没连上，
而失败原因（命令不存在 / 401 / 超时）只在主进程终端里。`addServer` 同理。

**修复方向**：`connectServer` 把错误透出（或至少把 `state.error` 放进返回值），UI 直接展示失败原因。

## P2-2 · 三处死代码，其中一处是本该存在的参数校验防线

**严重度**：中低（但与 P1-3 叠加后变危险）

| 死代码 | 位置 | 说明 |
| --- | --- | --- |
| `mcpInputSchemaToZod` | `app/mcp/bridge.ts:44` | 只被 `app/mcp/index.ts:38` 再导出，**无任何消费者**。MCP 工具参数因此从不校验 —— P1-3 的空参数直接穿透 |
| `mcpToolToToolDefinition` | `app/mcp/bridge.ts:32` | 同上，无消费者。它生成的 id 是 `mcp:<serverId>:<toolName>` |
| `planMCPToolRegistration` 的反注册过滤 | `core/mcp/router.ts:438` | 过滤 `id.startsWith('mcp:')`，但实际注册用的 id 是 `mcp_...`（`tool-id-registry.ts`）。**永远匹配不到**，形同空转 |
| `getMCPToolsForAI` 的 `useCondensed` | `app/mcp/bridge.ts` | 参数被 `void useCondensed` 直接丢弃 |

`mcp:` 与 `mcp_` 两套 id 规范并存，是这几处漂移的共同根源。

## P2-3 · 能力刷新不通知订阅者

**严重度**：低

`CoreMCPClientRuntime.refreshCapabilities`（`client-runtime.ts:96`）直接改 `this._state`，
**不调 `adapters.onStateChange`**（而 `connect`/`disconnect` 都会调）。
目前无人订阅所以没炸；一旦 P2 接了 `subscriptions/listen` 做增量刷新，这里就是状态不同步的现成坑。

## P2-4 · 权限授予不带 server 身份，跨 server 复用

**严重度**：低（窄口）

`resolveMCPPermissionResourceName`（`core/engine/tool-orchestration.ts:663`）取 `args.tool` / `args.function` 作为
权限 resource，而 `getMCPFunctionRefs`（`router.ts:167`）在工具名**全局唯一时 id 就是裸工具名**
（只有重名才加 `serverName/` 前缀）。

于是"永久允许 `search`"这条 grant 不含 server 身份：
删掉 server A 后新加的 server B 若也叫 `search`，旧 grant 会**直接命中新 server 的工具**。

（好消息：整体粒度设计是对的 —— 权限问的是目标 MCP 工具而非 `mcp_search` 本身，
`isReadOnlyMCPRouterCall`（`:659`）也正确豁免了 search/list/describe。）

**修复方向**：grant pattern 一律用 `serverId:toolName` 全限定，而不是展示用的 id。
