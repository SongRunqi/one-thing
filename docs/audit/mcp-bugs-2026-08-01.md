## ✅ P0-1 · web 端 MCP 工具对模型完全不可用（双管理器分裂，且静默）

**严重度**：高 · 功能整体失效 · 无任何报错

**根因**：服务端存在**两个互不相干的 MCP 管理器**。

- `/api/mcp/*` 走 `apps/server/src/runtime.ts` 的 `getOwnerMCPManager()` —— 一个 **per-owner 的 `HeadlessMCPManager`**。
- 而引擎执行工具走 `app/mcp/bridge.ts` 的 `coreMCPBridgeRuntime`，它硬绑在 **app 层单例 `MCPManager`** 上
  （`app/engine/stream/tool-execution.ts`、`stream-processor.ts` 均从这里取）。
- `createRealServerBackend` 的 `createOnethingBackend({...})` **没有传 `mcpAcp`**，
  而 `backend.ts` 的 `MCPManager.initialize()` + `registerMCPTools()` 只在 `options.mcpAcp` 为真时执行。
- 第二半：server 的 MCP adapter 里 `registerTools: async () => {}` 是**显式 no-op**，
  于是即使连上了也不会重新生成工具目录。

对照：桌面端在 `main-process.ts` 单独调 `initializeMCP()`；CLI daemon 传了 `mcpAcp: true`。
**只有 apps/server 两条路都没走。**

**触发条件（订正）**：服务端 MCP 连接默认是**关闭**的，需 `ONETHING_SERVER_MCP_CONNECTIONS=1` 才真连
（默认走 `DisabledServerMCPClient`，状态 `error` + "MCP connections are disabled in the web server runtime."，
这个默认行为是对的）。**一旦运维打开该开关**，才会出现"UI 显示已连接、工具列表也拉得到，但模型看不到 `mcp_search`"的静默失效。

**修复**：默认 owner 改为复用 app 单例，scoped owner 保留隔离——沿用这个文件里 `useAppSubsystems(context)` 的既有判例。
- `app/mcp/manager.ts` 新增 `configureMCPClientHost(factory)` 端口（late-bound，与其他 `configure*Host` 同构），
  让宿主注入自己的客户端实现，而不是另起一个 manager。server 由此把 `ServerMCPClient`
  （含 `ONETHING_SERVER_MCP_STDIO` 门控）与 `DisabledServerMCPClient` 交给单例，**stdio 门控与"默认不连"语义原样保留**。
- `apps/server/src/runtime.ts`：把单例塞进 `mcpManagersByOwner` 的默认 owner 槽位
  （`ServerMCPManager` 与之同型，9 处调用点零改动），`registerTools` 对默认 owner 改接 `registerAppMCPTools`，
  并在启动时非阻塞 `initialize + registerMCPTools`（与桌面对齐）。
- shutdown 自动覆盖：单例现在就在那个 map 里，原有的清理循环会带上它。

## ✅ P0-2 · 关掉再打开 / 修好配置后不会重连

**严重度**：高 · 高频用户路径

**根因**：`updateMCPClientConfigWithAdapters` 用 `wasConnected = state.status === 'connected'` 决定要不要重连，
而 `HeadlessMCPManager.updateSettings` 对**已存在的 client** 一律走 `client.updateConfig(config)`；
`disconnectServer` 只断开、**不从 `clients` map 移除**。于是：

| 场景 | 修复前 |
| --- | --- |
| 从未启用过的 server 打开 | ✅ 正常（map 里没 client → 走 `connectServer`） |
| 启用→连上→关掉→**再打开** | ❌ client 存在且 disconnected → `wasConnected=false` → 只改配置不连接 |
| 启动时连接失败（status=`error`）→ 用户改命令想修好 | ❌ 同上 → 不会重试，界面继续红着 |

第二种最疼：命令打错了，改对之后保存，依然红。

**修复**：判定从"镜像当前状态"改成"向配置目标收敛"——`shouldConnect = config.enabled`。
另外把重连失败**收进 try/catch**：新配置已经被调用方持久化了，此时抛错会让 UI 报"保存失败"而其实已保存；
现在改为返回 `markMCPServerError(state, error)`，保存成功、失败原因落在服务器状态上。

## ✅ P1-1 · MCP 工具返回的图片被 JSON 序列化成文本灌进上下文

**严重度**：高（保真 + 上下文炸裂双重）

**根因**：模型调 MCP 工具的**唯一路径**是 router。`executeMCPBridgeTool` 拿到结果后无条件
`mcpContentToString` 再包成单个 text part，而该函数对非 text 项是 `JSON.stringify(item)`——
image 项形如 `{ type:'image', data:'<整段 base64>' }`，于是整段 base64 变成文本。

**影响**：playwright / chrome-devtools 这类返回截图的 server，既拿不到图，又把几百 KB base64 当文本计费。
与之前修过的"图片 base64 以文本进请求"是同一类洞，MCP 这条路没覆盖到。

**修复**：
- `executeMCPBridgeTool` **原样透传工具自己的 content parts**；
- `mcpContentToString` 降级为"预览/进度行专用"：二进制部分只出 `[image: image/png]` 这样的摘要，永不序列化 payload；
  `resource` 带 `text` 时按可读文本处理。

**补修（同日 review 发现，第二次提交）**：只透传 content 还不够。
agent-loop 的 `toolOutputToText`（`core/agent-loop/tools.ts`）对**没有 `output` 字段**的负载直接
`JSON.stringify`，而 MCP 结果正好没有 —— 于是 base64 被灌进工具消息文本一份、
又作为真正的 image part 附一份，**同一份字节计费两次，比修之前更贵**。
`MCPToolCallResult` 因此增加 `output?: string`，由 `executeMCPBridgeTool` 在 router 与直呼两条路径统一附上摘要。

链路已逐段核对：`AgentToolResult.data = MCPToolCallResult` →
`addStructuredResultParts` 读 `content[]` 并映射 `part.data`/`part.mimeType` →
按 `toolResultModalities` 门控进 provider 的 image block（claude/codex 均声明 `['text','image']`）。

## ✅ P1-2 · 只要填了任意一个 env 变量，主进程整个环境（含各家 API key）就泄漏给 MCP 子进程

**严重度**：高（安全）· 且行为不一致

**根因**：`mergeMCPEnvironment` 里 `if (!customEnv) return undefined` / 否则 `{...process.env, ...customEnv}`。

- 不填 env → 传 `undefined` → SDK 用 `getDefaultEnvironment()` 的**安全白名单**
  （实测非 Windows 只有 `HOME/LOGNAME/PATH/SHELL/TERM/USER`）。
- 填了**任意一个** → 我们把 **`process.env` 全量**合并后传下去。

于是"给某个 MCP server 加一个 `GITHUB_TOKEN`"，会顺带把所有 provider 的 API key、OAuth token、
`ONETHING_*` 配置交给这个第三方子进程。用户不会预期，UI 也无提示。

**修复**：不再合并 `process.env`。改为**两条路径统一**——始终返回
`{...MCP_INHERITED_ENV_VARS 白名单, ...customEnv}`。白名单刻意极小且无密钥，只收
代理（`HTTP(S)_PROXY`/`ALL_PROXY`/`NO_PROXY` 及小写变体）与 `LANG`/`LC_ALL`——
这些是"缺了会静默失败"的（内网代理下 stdio server 连不上网，且没有任何错误指向 env）。
其余一律由每个 server 自己的 `env` 配置显式声明。测试补了"`ANTHROPIC_API_KEY` 不得随行"的断言。

## ✅ P1-3 · 模型把 arguments 传成 JSON 字符串时，工具以空参数静默执行

**严重度**：中高 · 静默错误

**根因**：`objectArgument` 只认真正的 object，**字符串一律返回 `{}`**。
模型（尤其经 openai-compatible 通道）把嵌套参数二次编码成 JSON 字符串是常见行为，
一旦发生，MCP 工具会**带着空参数被真的执行**，返回一个语义上莫名其妙的结果，既不报错也不提示。

**修复**：换成 `parseRouterArguments`——object 直接用；字符串先 `JSON.parse`，
解析出对象才用；解析失败或不是对象则**返回明确错误**（提示"send arguments as an object, not a string"），
不再静默降级成 `{}`。`undefined`/`null`/空串仍视作合法的无参调用。

## ⬜ P1-4 · 工具调用超时后串行锁提前释放，同一 server 会出现并发请求

**严重度**：中 · **未修，留给 v2 迁移**

`CoreMCPClientRuntime.callTool` 用 `toolCallQueue` 串行化（注释写明 stdio / 有状态 server 不耐受交错请求），
但超时是 `withMCPTimeout` 的 `Promise.race`——**只让我们这边的 promise 落地，底层 `client.callTool` 仍在飞**，
队列因此提前放行下一个调用，恰好破坏了这段代码想保证的不变量。

**为什么不现在修**：正确的修法是超时时向服务端发 `notifications/cancelled` 并等确认后再放行，
而取消语义在 2026-07-28 规范下由 v2 客户端承担（现状文档 R4 同源）。现在单独实现一套会白写。

## ✅ P2-1 · 连接失败被吞，UI 报"成功"

**严重度**：中

`HeadlessMCPManager.connectServer` 的 `catch` 只 `console.error`（这对启动阶段是对的——
一个坏 server 不该拖垮其余）。但 `connectOnethingMCPServer` 随后无条件 `return { success: true }`，
于是点"连接"永远成功，真实原因（命令不存在 / 401 / 超时）只在主进程终端里。

**修复**：`connectOnethingMCPServer` 连接后回读 `getServerState`，
`status === 'error'` 则返回 `{ success: false, error: server.error }`（并带上 server 状态）。
manager 的吞错语义保持不变，只是把结果读了出来。`OnethingMCPServerStateLike` 相应补 `error?: string`。

## ✅ P2-2 · 工具 id 映射表在生产里从未被填充（审查中新发现）

**严重度**：中 · **原条目是"死代码"，深挖后发现是真 bug**

`CoreMCPToolIdRegistry.rememberTools()`（sanitized-id → `{serverId, toolName}` 映射）
**只能经由 `buildToolsForAI` 到达，而它唯一的调用者 `getMCPToolsForAI` 已经是死代码**
（模型可见的工具列表早已改走 `getMCPRouterToolDefinition`）。
结果：`sanitizedToOriginalMap` 永远是空的，`parseMCPToolId` 与 `findMCPToolIdByShortName`
一直在跑兜底路径（前缀切分、按参数名猜工具），而不是真正的映射。

**修复**：`CoreMCPBridgeRuntime` 新增 `rememberToolIds()`，由 `registerMCPTools()` 调用——
那正是"连接的工具集发生变化"的时刻（连接/断开/改配置都会经过），side effect 放在语义诚实的位置。

**仍存的死代码（未删，无害且有测试覆盖）**：`mcpInputSchemaToZod`、`mcpToolToToolDefinition`、
`getMCPToolsForAI`；以及 `planMCPToolRegistration` 里过滤 `mcp:` 前缀的反注册（对 `mcp:<serverId>:<tool>`
这个 id 形状是正确的，只是如今没人注册 per-tool id 了）。
根源是 `mcp:` 与 `mcp_` 两套 id 规范并存——建议随 v2 迁移一并收敛。

## ✅ P2-3 · 能力刷新不通知订阅者

**严重度**：低（潜伏）

`CoreMCPClientRuntime.refreshCapabilities` 直接改 `this._state`，**不调 `adapters.onStateChange`**
（而 `connect`/`disconnect` 都会调）。目前无人订阅所以没炸；一旦 P2 接了 `subscriptions/listen`
做增量刷新，这里就是现成的状态不同步坑。

**修复**：改为构造 `nextState` 后走 `onStateChange`，与 connect/disconnect 对齐。

## ✅ P2-4 · 权限授予不带 server 身份，跨 server 复用

**严重度**：低（窄口，但属权限正确性）

`resolveMCPPermissionResourceName` 取 `args.tool` / `args.function` 作为权限 resource，
而 `getMCPFunctionRefs` 在工具名**全局唯一时 id 就是裸工具名**（只有重名才加 `serverName/` 前缀）。
于是"永久允许 `search`"这条 grant 不含 server 身份：删掉 server A 后新加的 server B 若也叫 `search`，
旧 grant 会直接命中新 server 的工具。

**修复**：`buildMCPPermissionPlan` 增加可选 `resolveServerId`，grant resource 改为全限定
`mcp:<serverId>:<toolName>`（解析不到 serverId 时回退原样），**审批弹窗仍显示友好名**。
解析器从 bridge 透传下来：`resolveMCPServerIdForToolRef` → runtime `direct-tool-execution` → core。

> 注意：grant key 形状变了，**已有的 MCP 永久授权会失效一次**，需要用户重新批准一次。这是预期内的。

（整体粒度设计本来就是对的——权限问的是目标 MCP 工具而非 `mcp_search` 本身，
`isReadOnlyMCPRouterCall` 也正确豁免了 search/list/describe。）
