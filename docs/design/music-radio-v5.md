## 1. 验尸:三个症状,一个根因

### 现场证据

- 节目单新批的 `title` 是**裸歌名**:`'泥土'`、`'Slow'`、`'早春的树'`——DJ 这一批没带
  " - 歌手"后缀(上一批带了;LLM 手写字符串,格式漂移是常态而非事故);
- 播放器 `state` 上报的 title 是 `'早春的树 - 陈鸿宇'`(name - artist,机器格式,稳定);
- app.log:`22:46:55 开始播放 早春的树` → `22:51:00 开始播放 早春的树`(完整放完一遍再来一遍);
- brief.played 里记录的是播放器格式(带歌手),节目单/收件箱里是 DJ 格式(裸名)。

### 断裂链

系统里所有"这首歌是谁"的判断都在拿 **title 字符串**当键,而 title 有两个互不一致的来源
(DJ 手写 vs 播放器上报):

| 功能 | 匹配逻辑 | 断裂后果 |
| ---- | ---- | ---- |
| 串词(人声) | `pendingPatter.get(sample.title)` / `onDeck.title === sample.title` | 裸名 ≠ 带歌手名 → 永远查不到 → **人声全灭(症状三)** |
| 歌词 | `lyrics.title === nowPlaying.title` | 同上 → **placeholder 永远空(症状二)** |
| 跨批次去重 | mergeInbox 用 played 的 title 兜底(played 无 id 可用) | played 记的带歌手名,新批写裸名 → 去重失效 → **同一首歌被新批重新收录 → 放两遍(症状一)** |
| 红心 | `nowPlaying.title !== onDeck.title` 即拒绝 | ♥ 按钮误报"不知道这首歌的 id" |

次要助攻(症状一的另一翼):`play` 走的 transport 类带 **1 次自动重试**,而 play **不幂等**
——"报错但实际起了声"(controller disconnected 一类)加重试 = 再起一遍。日志里 20:2x
成对出现的 boot+失败就是它的痕迹。

### 根本教训

**LLM 手写的字符串永远不能当关联键。** 我们其实早有这条教训的兄弟版本("绝不凭记忆编造
id"),但只防了 id,没防 title。而且 legacy 播放世界里有个被忽视的架构红利:**每一首歌都
是我们亲手起播的——"现在放的是哪首"根本不需要猜**,onDeck(带双 id)就是事实本身。
title 匹配这一整层逻辑,是从"播放器自己推进队列"的旧世界遗留下来的化石。

## 2. 修复方案:锚定重构(id-anchored)

### 2.1 spins 带 id,去重按 id

`played/skipped/loved` 的记录从 `{title, at}` 升级为 `{title, at, encryptedId?}`
(title 仅展示)。mergeInbox 的跨批次去重改为:**encryptedId 命中即拒**(programme 现存 +
played 近 50 的 id 集合),title 兜底降级为"完全一致才拒"(容忍展示差异,防误杀翻唱)。
→ 直接修死"同一首歌跨批次回锅"。

### 2.2 串词/歌词/已播:全部移到起播成功点,删除 title 匹配层

legacy 世界每次起播都经过 `playProgrammeEntry(entry)`,它拿着完整的 entry(id/say/title):

- **verify 成功当场**:speak(entry.say)、pushLyrics(entry.encryptedId)、
  recordPlayed(entry)——不再等 watcher 的 title 到达,不再有任何字符串匹配;
- conductor 的 `pendingPatter` map、title-change 触发 speak、lyrics 的 title guard、
  ♥ 的 title 校验——**四处 title 匹配逻辑整层删除**;
- 歌词/串词的推送顺带带上**播放器上报的 title**(verify 的 state 里有),renderer 展示
  用它,与状态栏天然一致;
- 副产品:串词时机更准了(歌头即说,不再有 0~5 秒的轮询延迟)。

### 2.3 play 零重试 + 迟到成功补偿

- `play` 从 transport 类(1 重试)改为**零重试专类**——非幂等命令不许自动重演;
  可靠性由"轮询 verify + conductor 下一 tick"承担,这本来就是它们的职责;
- **onDeck 在发出 play 时就记录**(而非 verify 成功后):这样"12 秒 deadline 判负、
  第 13 秒出声"的迟到成功不再级联(conductor 见 playing + 起播失败旧错时,清错并按
  onDeck 补推歌词/串词——补偿钩子一处搞定)。

### 2.4 编排调度:里程驱动(上轮已议定,并入本批)

- 续批资格 = 自上次续批后真实播掉 ≥3 首(播放是燃料;不播不编);
- 失败重试事件化(下一次播放事件才可重试)+ 失败分类(环境类零重试直接熔断、
  配额类冷却到窗口刷新、偶发类允许一次);
- 批次加大到 15~20 首;跳歌密集(10 分钟 ≥3 次)作为强事件可提前触发换向编批;
- 现有的时钟退避/熔断保留为最后防线,但正常路径不再靠它。

## 3. 升级方案:Music 工作区(用户定案的 UI 方向)

**编排保留会话形态**(headless 方案搁置——可审计、可对话、复用全部 chat 基建),
但从公共会话列表里搬走,给音乐一个自己的家:

- **sidebar 新增 Music 入口**(与现有分区并列,画线风图标);
- 点击进入 **Music 工作区**:
  - 主体 = **复用现有 chat 界面**(ChatContainer 等组件原样),加载电台会话——
    在这里看 DJ 编排、跟 DJ 说话、翻节目单历史;
  - 头部 = 电台状态条(当前播放/意图/节目单余量/lastError),数据全部现成
    (getRadio + nowPlaying);
  - 左列(或下拉)= **历史电台会话列表**——H1-7 的会话轮换在这里自然落位:
    转录超阈值就开新会话,旧的留在列表里,不再是"侧栏里自己动的幽灵";
- **Session List 过滤**:`agentId === 'radio-dj'` 的会话不再出现在公共会话列表
  (实现在 sessions 列表的取数层,一处过滤);
- 电台会话的一切自动行为(唤醒、标题抑制、无人值守即拒)不变——只是换了个住处,
  从"混在你的对话里"变成"在 Music 的后台房间里"。

## 5. 波及与风险

- 2.2 删除 title 匹配层会改 conductor 的 speak 通路 → conductor 测试约 6 处重写;
- spins 加 id 是向后兼容扩展(normalize 容缺);旧 brief 的 played 无 id → 去重对
  历史条目退化为 title 精确匹配,一天后自然换血;
- Music 工作区不改会话数据结构,只改取数过滤与路由——回滚 = 删过滤;
- 模型手动 play(绕过 playProgrammeEntry)的歌仍无歌词/串词/红心——既有边界,不变。
