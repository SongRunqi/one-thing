# 同事的视野 —— 已读游标 / 未读块 / 按天折叠

2026-08-01。起因是一次真机事故复盘(cumo 房,17:53–17:57)。

## 1. 事故与根因

用户报的现象:Bram 说完话之后,他自己的会话里立刻又出现一条
`<turn agent="Bram" reason="被 @激活">`,看起来像"自己 @ 自己把自己叫醒了"。

查下来**不是自激活**——`state.json` 里 50 条激活记录逐条回查触发消息的作者,
self-activation = 0/50,`decideCollabActivations` 那道 `agentId !== authorAgentId`
过滤是好的。

真正的根因是**队列积压 + 陈旧激活**:

| Bram 被驱动 | 触发消息 | 作者/时间 | 陈旧度 |
| --- | --- | --- | --- |
| 17:55:16 | `74809f02` | Nova 17:53:45 | 91s |
| 17:55:56 | `1fa04bb1` | Iris 17:54:05 | 111s |
| 17:56:31 | `74dc01b4` | Nova 17:54:26 | **125s** |
| 17:56:55 | `a39c37b8` | Atlas 17:55:13 | 102s |

四条都是别人真的 @ 了他,但每条回合 20–35 秒,而每个回合又级联出新的 @。
于是每次开口应的都是两分钟前那句早被别人答过的话——群里出现三遍
「四人全齐 @Iris 喊天黑」;而所有人都在等的 Iris 排在队尾,一次都没轮到。

**一个 @ = 一个必须兑现的回合**这条换算是病根。并行化只压缩墙钟,不减一条重复
发言(同一个人仍被 `isAgentSpeaking` 串行)。

## 2. 模型:从债务制到游标制

- **债务制**(旧):每条消息对每个人生成一笔"你欠一次回应"的记录,记录要去重、
  要 park、要跨重启复活,还要靠 W23 扫 transcript 证明"这笔债还过了"。
- **游标制**(新):每位同事在每间房有一个"我读到哪儿了"。被唤醒时它看到的不是
  某一条消息,而是**一个未读区间**。

推论:**未读区间本身就是持久化的待办**,所以激活记录退化成一个没有身份的敲门
声——"去看看",而不是"你欠这条一次回复"。

## 3. 两条不可让步的约束

1. **未读永不丢。** 离开三天的同事,未读横跨三天也要逐字给到。折叠掉未读是这套
   机制唯一能造成的不可逆伤害。
2. **切点必须稳定。** provider 前缀缓存按前缀命中——真机 `cacheRead` 命中率
   99.1%,单价是 `input` 的 1/120(0.003625 vs 0.435)。因此:
   - **按天切**(稳定切点)→ 一天只 miss 一次,之后全命中;
   - **最近 N 条**(滑动窗口)→ 每来一条消息前缀整体位移,工具定义 + 人设 +
     全部历史一起掉出缓存,**发的字更少而单回合贵 8–20 倍**。

第 2 条同时决定了未读块的**位置**:插进 `<History>` 中间会让插入点之后的一切
每回合都变;追加在 `</ChatRoom>` 之后则前缀零改动,而且落在上下文末尾——
指令遵从最强处,与 drive 行同一个论证。

## 4. 三路分派

```
已读 且 早于切点     → 折叠成一行 <Folded count from to/>   （<History> 首行）
已读 且 在切点之后   → 逐字进 <History>                      ← 稳定前缀,全缓存
未读（无论多老）     → 逐字进 <NewMessages>                  ← 尾部,每回合变但很小
```

未读**不在 `<History>` 里重复**:下一轮游标前移,它们自然并入历史尾部,前缀单调
增长,缓存照旧命中。

载荷形状:

```xml
<ChatRoom id="…" name="cumo">
<Members>…</Members>
<History>
<Folded count="198" from="2026-07-28" to="2026-07-30"/>
<say from="Iris#eba0c4b7" time="2026-08-01 17:54">…</say>
</History>
</ChatRoom>

<NewMessages count="1" seen_until="2026-08-01 17:55">
<say from="Atlas#7185be2b" time="2026-08-01 17:56" rel="mentions-you">…</say>
</NewMessages>
```

`rel` ∈ `mentions-you` / `quotes-you` / `bystander`——**只在未读块出现**(历史里
是按条计费的固定开销 × 全量投影)。它是判定层的结构化抓手,不让模型纯靠语义猜。

## 5. 游标写入纪律

`session.collab.seenMessageId`(kind='agent' 的常驻会话——collab-team-v2 §1.1 已经
保证"每群每 agent 一条",所以这条会话本身就是那个键,不需要另开一张表;它跟着
transcript 一起活过重启,而这一点是必需的:事故里那批陈旧激活正是靠重启复活的)。

- **取值时机**:`emitDrive` **之前**取房间末条 id。投影是引擎在流启动时构建的,
  取得稍早 = 这几毫秒内到达的消息算未读——多读一遍是安全方向,反过来就是永久
  丢消息。
- **落盘时机**:`outcome === 'complete'` 才写。abort/超时的回合可能一个字都没读到。
- **沉默同样推进**:读过了、判断不必说,是有效处理。不推的话同一批未读会反复把
  它叫起来——那正是陈旧激活的机制。
- **只前进不后退**,按房间列表下标比大小(时间戳会撞、会因时钟回拨乱序)。
- **自己说的话永远不算未读**——那是它写的,不是它错过的。

## 6. 配置

`session.room.context`(与 `budgets` 分开:那一格是花钱的闸,这一格是"给模型看
多少",混在一起迟早有人把省钱和省上下文当成同一件事):

| 字段 | 默认 | 0 的含义 |
| --- | --- | --- |
| `historyDays` | 1(只留今天) | 不折叠,全量 |
| `historyTailCount` | 20 | 不额外保留(日界悬崖不堵) |
| `unreadMax` | 50 | —— 超出的**退回历史**并记 `elided`,不是丢掉 |

## 8. 分期

- **P0 ✅** 游标存储 + 尾部 `<NewMessages>` + `rel` + 提示词两句
- **P1 ✅** `<History>` 按天切 + `<Folded>` 计数行 + 房配置
- **P2 ✅** 折叠段的每日一行滚动摘要(`collab/digest.ts` + `app/collab/digest-{store,runner}.ts`)。
  **后台触发,可关**:`room.context.dailyDigest`(缺省开)。回合收尾之后触发、
  不等待,所以今天第一个回合看到的折叠段还没摘要,下一轮才有。计费打
  `collab-digest`。摘要是 push、工具是 pull —— 摘要当主力,工具当兜底。
- **P3 ✅** `room_history(member?, since?, until?, contains?, limit, cursor?)`。
  输出复用 `<say>` 信封;硬上限 30 + 分页;**只查折叠段**(切点之后的本来就在
  `<History>` 里,再查一遍是重复付费);房作用域从会话推,**没有 room 参数**。
- **P4 部分 ✅**
  - ✅ 同 agent 的对话性激活**折叠成一个回合**(`queue.ts` `foldIntoQueued`)。
    只折叠**队里**的:已起跑那条的上下文早构建完了,折进去等于让新消息没人应。
  - ✅ **未读闸**:对话性激活轮到自己时若已无未读 → 不花那次全上下文调用
    (`turn.ts`,判据与投影共用 `planCollabHistoryWindow`)。任务事件/日程豁免。
  - ✅ 沉默也推进游标(P0 就位)。
  - ⏸ **判定层吃未读窗口**(输入换成「我上次说了什么 + 未读列表」,输出加
    `targetMessageIds`)。
  - ⏸ **agent@agent 取消 @ 短路**(用户 @ 仍强制 —— 那是产品承诺)。

  后两条**刻意留到下一轮**,而且必须一起做:取消短路之后,被 @ 的人要靠判定
  接住,而现在的判定既看不见未读、也不知道自己被点了名 —— 更糟的是
  `filterCollabSelfElectCandidates` 的冷却会把"刚说过话又被 @"的人直接筛掉,
  于是「点名必须能应」这条产品承诺会静默失效。这是一次提示词行为改动,要真机
  迭代,不该和结构改动混在一次里。
- 独立 ✅:`isCollabStopMessage` 词表 —— 用户打的「stop掉。」不匹配,导致喊停失效、
  `floorEpoch` 没换代、6 条陈旧激活跨重启复活。现在剥语气/趋向后缀(掉/吧/了/
  来/下…),**只剥后缀不剥前缀**(剥前缀会把「不要停」变成「停」)。

### P4 带来的一处行为变更(已在测试里明说)

已读游标是继 W23 两级去重之后的**第三级证明,而且更硬**:记录被挤掉、转录被
清空、drive 没有 `collabSourceMessageId` 戳 —— 这些情况过去都会重放一次,现在
不会了,因为那一轮**跑完过**(沉默也是跑完),消息是读过的。真正需要重放的失败
仍然重放:中止/超时/崩溃的回合不推进游标。

## 9. 这套机制**不**解决的

同一刻并行起跑的两个回合读到同一份未读,谁都看不见对方正在说的话,所以"两个人
说出意思几乎一样的话"仍然存在(事故里 Atlas 17:56:26 与 Bram 17:56:46 就是这么
撞的)。那需要抢麦判定(`qm-collab-learnings.md` P0-2:一次调用决定这轮谁说、
说几个),不是视野线能管的。
