案三取材台 Harvest
导航退到 26px 顶线，"带入对话"升为常驻底栏 + 素材篮。

前两案都在问「怎么把 Chrome 塞进窄面板」。本案换一个前提：这里不是 Chrome，是取材台。 用户开这个面板，十有八九是为了把页面上的某个东西喂给旁边的对话——那"拾取"就不该是最右角一枚 15px 的十字图标。 于是导航压到一条 26px 的顶线（标签变成 favicon 点阵，前进/刷新收进 ⋯）， 腾出来的注意力全给底部一条 34px 取材栏：拾元素 / 截当前屏 / 取正文 / 取链接，右侧是素材篮。 取到的东西先落篮，可增删、可一次性带入对话，而不是每拾一次就往输入框里塞一张图。 取向：把浏览器当作对话的输入设备，而不是第二个浏览器。

读长文时用：chrome 只剩 7px 提手 + 底部取材栏，点提手或 ⌘⇧H 恢复。

为什么这样

  • 控件的大小该按使用频率排：在这个产品里"带入对话"比"前进按钮"重要一个量级，现在两者都是 15px 图标。
  • 素材篮把"拾取 → 立刻塞进输入框"的单次动作改成可累积、可后悔的批处理，符合真实取材节奏（翻三段、截两图，再一起问）。
  • 底栏在拾取时直接变成状态条，不需要另造提示浮层——而浮层本来也会被原生视图盖掉。

落地要点

  • 「取正文」= 主进程 executeJavaScript 跑一次可读性抽取（现有拾取管线已能注入脚本），产出纯文本 + 来源 URL。
  • 素材篮是 renderer 侧的临时数组，"带入对话"时一次性 dispatch 多个 onething:composer-attach；token 估算按 base64 长度 + 文本长度粗算即可。
  • 收起态的"靠近上边缘自动恢复"做不了——鼠标在原生视图上，DOM 收不到 mousemove。只能点提手或用快捷键，别在设计里承诺 hover 恢复。
  • 标签点阵超过 8 个要降级：显示前 7 个 + 「+N」，点开走案一那样的下推列表。

代价

  • 纯浏览体验最差：切标签靠点小方块（7px 命中区偏小，需 hover tooltip 补），刷新/前进埋进 ⋯。
  • 底栏常驻吃 34px，总 chrome（60px）比案一还高——省的是注意力，不是像素。
  • 四个动作会不会真被用起来，取决于"取正文/截屏"的质量；做不好就是三枚永远不点的按钮。
