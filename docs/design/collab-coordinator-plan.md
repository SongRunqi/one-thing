# 协调器编排 —— 一次调用产出 waves

状态：**已实施**（2026-08-02）· 默认仍是并行，编排需显式打开
日期：2026-08-02
前置：`collab-speaking-order.md`（并行/接力两种模式，本设计取代其中的「模式」概念）、`qm-collab-learnings.md`（P0-2 抢麦判定 / P2-8 判定账本）、`collab-coordinator-inspector.md`（状态条，§8 待办是本设计的前置台阶）

## 0. 一句话

**一条用户消息 = 一次协调器调用 = 一份编排（plan）**，调度器机械执行它直到耗尽、撞闸或被打断。

---

## 1. 为什么

`collab-speaking-order.md` 把「并行 / 顺序」做成了房间的一个静态字段，由用户在设置里钉死。真机用下来这件事是别扭的：同一间房，「大家怎么看」该并行，「按顺序从 1 数到 10」该接力，而模式是一个开关。

用户的原话是「我需要协调器来做这件事情」——模式不该是配置，该是**协调器每一轮的现场决策**。

而一旦协调器要决定"这一轮怎么走"，它就必须同时回答**谁说**和**什么次序**；这两件事分开问是浪费，一次调用就能一起答。这正是 `qm-collab-learnings.md` 的 P0-2，只是从一个更好的入口到达：它的价值不是省钱（那是副产品），而是**让"怎么组织这一轮"变成可表达的**。

---

## 2. 支点：waves

```json
{
  "waves": [["atlas"], ["bram"], ["iris"], ["nova"]],
  "cycle": true,
  "why": "他们要按顺序数数,一直数到有人不接为止"
}
```

**`waves` = 有序的批次，批内并行、批间串行。** 就这一个概念。

| 场景 | 编排 | 旧方案需要 |
| --- | --- | --- |
| 大家怎么看 | `[[a,b,c]]` | 并行模式 |
| 从 1 数到 10 | `[[a],[b],[c],[d]]` + `cycle` | 顺序模式 |
| **A 先说，B 和 C 补充** | `[[a],[b,c]]` | **两种模式都表达不了** |
| **大家先议，PM 最后总结** | `[[a,b,c],[pm]]` | **表达不了** |
| 这轮谁都不该说 | `[]` | N 个人各花一次调用说 no |

**「模式」这个概念因此消失。** 并行是"一个 wave"，顺序是"N 个单人 wave"——它们本来就是同一个结构的两端；把它做成一个 `responseMode` 枚举，只是因为当时还没找到这个结构。

### 为什么是 `cycle`（布尔）而不是 `loop`（数字）

接力已经有一个比次数更好的终止条件：**走满一整轮 waves 没人开口就停**（现有的 `relayPassStreak >= 环长`）。

「数到 10」四人环，数完之后第 11–14 棒各自无话可说，走满一圈静默 → 停。**模型完全不必算出"四个人数到十要三圈"**——它容易算错，而算错的代价是数到 8 就停，或者空转两圈。

所以模型只回答它擅长的两件事（**谁、什么次序**）外加一个"这事是不是要一直轮下去"的布尔，**次数交给现实**。

- `cycle: false` —— 走一遍就停。多数场景。
- `cycle: true` —— 反复走这串 waves，直到走满一整轮全静默。

## 3. 三层职责

| 谁 | 决定什么 | 成本 |
| --- | --- | --- |
| **协调器**（一次调用） | 谁说、什么次序、要不要循环 | O(1) / 条消息，走便宜模型 |
| **用户**（房间设置） | 圈数天花板、模式强制、次序建议 | 0 |
| **机器**（零调用） | 什么时候停：一轮全静默 / 撞天花板 / 链闸 / 喊停 | 0 |

对比现状：并行是 O(N) 判定/条，接力是 0 判定但每棒空转。

---

## 4. 输入材料

**仲裁者不需要"成为"任何人**，所以 persona 不进 system prompt——这不是妥协，是这个形状的自然结果。system prompt 只写仲裁者自己的规则；下面这些全部作为 user 段的**数据**：

- 房间名 + 群规（若有）
- **花名册每人一行**：名字 / 头衔 / 一句职责 / 状态（在跑、刚说过、名下在飞的卡）。不是 persona 原文——仲裁者要的是一份目录，不是 N 份人格。
- 游标之后的**全部新消息**（带 `[id]`、作者、@ 到谁），游标之前 N 条作只读背景
- **已定的约束**：用户强制的模式、次序建议、闸的余量（链还剩几条、预算还剩多少）

## 5. 执行

```
一条用户消息
  → 一次协调器调用 → plan
  → 执行 waves[0](批内并行,受 maxConcurrentTurns)
  → 等这批全部跑完 → waves[1] → …
  → cycle ? 回到 waves[0] : 停
```

**plan 干净走完（exhausted）→ 续排**（2026-08-02 用户改定，推翻同日早先的「耗尽就停，等人说话」）：泵再问协调器一次「要不要继续」——空 waves = 收工（正常答案，提问句里明写），有 waves = 装新编排接着跑。四道闸让它不是失控入口：

- **只接 `exhausted`**。静默圈 / 圈数闸 / 链闸 / 被顶掉 / 全军覆没各有自己的收尾语义，都不续；
- **`spokeEver` 门**：整趟没人开过口不续——材料没变，再问只会得到同一个答案，而链长闸只数说出的话，拦不住静默循环；
- **真实用户消息永远压过续排**（ticket 在续排入口、第一个 await 之前取）；预算闸先过；
- **链长闸是所有续排轮次的总闸**：每轮的发言都计入 `chainCount`，到即停。

续排的提问句整个换掉（`plan.ts` `continuation`）：初排那句「最后一条消息就是任务」在这里是毒药——续排时最后一条是某位同事的发言，沿用会把它读成要应答的新指令，一续就停不下来。只限 `auto` 房；强制顺序不问协调器，它的一趟以静默圈/圈数闸收尾。要不到续排编排**不降级**到 N 路判定——续排失败的正确形态就是停下。

**空编排不是终审**（2026-08-02 用户定，真机死锁催生）：编排器答「这轮无人发言」——初排或续排——之后**回落 N 路意愿判定**，每位同事自判是否响应；没人自荐才是真的沉默（那条老路自己消费消息）。真机抓到的死锁：续排答「规则已拟出，等待大家反馈，无需继续安排发言」却排零人——"反馈"恰恰需要有人说话，而"等"不是编排器有的动作。职权划分由此定型：**编排器定次序与批次，"是否响应"归每人自己的意图判断**。提示词同步钉死（system 段 + 续排提问句）：You never "wait"——期待成员反馈就把他们排进批次，空编排=线索关闭。区分要严：只有「答了且答空」回落自判；静默圈、圈数闸、链闸、续排失败都不回落（各有收尾语义）。回落自判前过链的自荐上限（与回合级联同一道闸），刚说过话的人被冷却筛掉。

用户插话 → 旧 plan 作废、新调用（复用现成的 floor 世代号）。撞闸 → 停。

### 三条必须由代码兜住、不靠模型自觉

1. **被 @ 的人一定在 plan 里。** 解析完之后把被 @ 却漏掉的人插进 `waves[0]`。「点名必须能应」不能交给模型的注意力。
2. **plan 里不在册 / 已退休的 id 直接丢**，不报错——模型会记错名字，这是常态。
3. **plan 有长度上限**（waves × 循环 ≤ 某个数），与链长闸各管一头。

### 降级

plan 解析不出来 / 超时 / 花名册过大 → 回落现有的 N 路意愿判定。所以 `judgeOne` 那条链**不退役**，它是降级路径——这也是为什么 `collab-coordinator-inspector.md` §8（给判定加 `outcome`、补计费）要先做：换发动机之前得先有仪表。

## 5bis. 落地与设计的三处出入（2026-08-02）

设计写完到跑通之间改了三个决定，都记在这里而不是悄悄改上面的正文。

### 一、`auto` **没有**作为新默认

设计说"auto 作新默认"。落地时没跟着翻：**机制和默认翻转放进同一个改动，任何一个 bug 都会一次性铺满每一间既有房间**。而且证据是硬的——把默认改成 auto 之后，`collab` 两棵测试树里约 100 个用例同时变红，它们编码的正是旧默认的行为。

现在 `responseMode` 未配 = 并行（与今天一字不差），`auto` / `serial` 才走编排。先让它可显式打开、真机跑过，再谈翻默认。

### 二、推进在**调度泵**，不在回合收尾

设计 §6 的映射表把 `shouldPassCollabRelayBaton` 直接对到 `shouldAdvanceWave`，读起来像是"还在 turn.ts 里推进"。那样不行：一个 wave 可以有 N 个回合，而"这一批完了没有"只有泵知道；留在回合那边，同一批的兄弟回合会互相误判成"另一根棒子"。

所以推进口只有一个：`processQueue` 里 `tasks.size === 0` 的那一刻。`turn.ts` 只留两件回合自己才知道的事（这一批有人开口了、它在发言里 @ 了谁）。

### 三、`maxConcurrentTurnsFor` **不再为顺序模式恒返回 1**

接力时代"依次"是靠并发上限压出来的。编排之后串行由**批边界**保证，而批内是并行的——继续恒返回 1 会把批内并行悄悄压成串行，而且没有任何地方会报错。这一格因此回到它本来的意思（同时最多几个人说话），并且在**每一种模式**下都生效、都可编辑。

## 6. 现有接力代码的去向

**接力是 waves 的一个特例**（环 `[a,b,c,d]` = waves `[[a],[b],[c],[d]]`），所以上一轮做的东西基本都留着：

| 已有 | 变成 |
| --- | --- |
| `relayPassStreak` | `wavePassStreak`（连续几个 wave 没人说） |
| `relayBatons` | 已执行的 wave 数 |
| `shouldPassCollabRelayBaton` | `advanceCollabPlan` —— 终止逻辑几乎逐字保留，`ringLength` → `waves.length`。**调用点从回合收尾搬到了调度泵**，见 §5bis 二 |
| 「一根棒子」不变量 | 「一间房一份在飞的 plan」 |
| @ 抢棒 | @ 插进 `waves[0]` |
| `relayLoops` | 原样保留，语义从"计划的一部分"变成**天花板闸** |
| `responseMode` | `'auto'`（协调器定）/ 强制并行 / 强制顺序。**缺省仍是并行**，见 §5bis 一 |
| `speakOrder` | 降级成给协调器的**次序建议**（仍进材料，模型可以不听） |
| `buildCollabRelayRing` / `pickCollabRelayStarter` | **没退役** —— 它们变成 `synthesizeCollabSerialPlan` 的内脏:强制顺序不问协调器,本地按次序表合成一份"所有批都只有一个人"的编排。于是执行器只有一套 |
| `pickCollabRelayNext` | 退役 —— 环的"下一位"由 waves 直接给出 |

## 7. 状态条的副产品

`why` 直接进「刚才」：

```
0:02  编排 阿般→小李→Iris→老丁 ↻(他们要数数)
```

**用户第一次能看到协调器为什么这么排。** 现在的「判定 3 人 → 都没接话」连"为什么"这个字段都没有。

---

## 8. 已知风险

**plan 是预测，现实会偏离。** A 说完话题拐了，后面的 waves 就排错了。

不打算用"每个 wave 前重新判一次"去补——那把 O(1) 又变回 O(N)，回到原点。处理是：**接受偏离**，靠 plan 长度上限 + 用户随时能停 + **编排理由可见**（排错了一眼看得出来）。

现在的接力也是盲的，区别只在于：接力盲得没有理由，plan 盲得有理由可查。

**单点风险**：一次调用决定所有人的命运，答错就是整屋子沉默或整屋子乱说；N 路判定至少是分散的。所以 P2-8 判定账本要和它一起做——而 §5 说的"先做仪表"就是这件事的第一级台阶。
